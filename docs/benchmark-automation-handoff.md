# 竞品对标自动采集：开发移交说明

> 日期：2026-10-17。接手者请先检查当前工作树和运行中的服务，再以实际代码及数据为准。**本文是待开发任务的移交，不是已实现功能的说明。**

## 用户真正要的结果

用户要的是 **AI 已经为对标账号打开浏览器抓取时，顺带自动填好该账号的头像、主页可见资料和约 5 篇主页可见笔记的数据**。不应在抓完账号后留下空卡片，再让用户逐张点“补齐”。用户发起一次推荐/核实/抓取任务后，系统应在同一次流程或自动接续的有界队列里完成身份核实、主页与头像观察、逐篇笔记观察、保存和页面更新。已经登记但缺少这些数据的旧条目应有**一次性批量补齐/恢复**入口，而不是逐卡操作。登录、验证码、风险提示仍只能由用户本人处理；没有页面证据的字段留空，不得臆造。

此处“约 5 篇”指主页当前**可见、可核对链接的前 5 篇**；没有证据证明时间排序时不要标成“最新 5 篇”。深度规律拆解仍由 agent 做。**自动发布、自动评论和多账号功能必须保留**，不能为完成本功能移除或改为单账号。

## 上一轮完成了什么，以及关键偏差

已有能力（代码在工作树，未提交；接手者勿先清理/重置）：

- `xhs-workbench/server/browser-worker.mjs:182`：可选有头只读 worker 在单次 `verify()` 中核对当前登录账号、目标主页身份、尝试截头像元素、读取主页字段和最多 5 个可见笔记链接，并对每篇回调。
- `xhs-workbench/server/bridge.mjs:209`、`xhs-workbench/server/server.mjs:63`：同账号浏览器资料互斥，worker 回调按主页/逐篇写核实及观察检查点。worker 确定字段不调用模型；登录/风控/资料占用不绕过。
- `xhs-workbench/server/content.mjs:157`、`xhs-workbench/server/benchmark-observation.mjs:137`：校验检查点并把观察合入每个对标目录的 `snapshot.json`；字段保留来源和观察时间，笔记按 URL 合并，拒绝身份冲突/坏头像，已写入的部分可在超时、取消或重启后保留。`notes.json`/`report.md` 仍是独立的 agent 分析数据。
- `xhs-workbench/web/modules/benchmark.js:135`、`:204`：列表改头像卡片，详情默认显示结构化主页与笔记观察、缺失原因和来源；手动头像是带标记的回退。旧条目未观察到的头像/笔记不会伪造。
- `xhs-workbench/playbooks/benchmark.md:139`：worker 关闭时，agent 可用独立观察检查点写入同一数据合同。

**错误的产品接线**：`web/modules/benchmark.js:323` 的“推荐”仍明确要求 agent **不开浏览器、只给候选，写完再问用户是否核实**；`:325` 的采集只挂在用户进入**单张卡片**后点按钮。`server/server.mjs:314` 的 `sendChat()` 只有显式 `benchmark.verify`/`browser.prepare` 任务入口；检查点合并和 SSE 更新并不自动生成后续采集任务。`server/automation.mjs` 的雷达定时任务是“发现新笔记/爆款”的 agent 流程，不会补 `snapshot.json` 或头像。也就是说：**底层能一次采、能显示，但发现/核实/agent 浏览器抓取与自动补齐未串起来**。这正是当前任务的 P0 缺口；不能用“用户逐卡点击”当作已解决。

上一轮 `npm test` 为 **67/67 通过**，其中真实 HTTP、假 agent、假浏览器与手机宽度 UI 冒烟测试仅证明代码链路和版式；**没有真实小红书页面的头像/笔记 DOM 验证**。当时本机 `playwright-core@1.64.1` 已安装，但 `browser-worker-status` 显示后台采集**未启用**；原有工作台进程仍在运行且未因修改自动重启。此前真实有头抓取验证被权限系统拒绝，不能绕道重试或把模拟数据写进真实账号。接手时先复核实时状态，不要假设仍相同。

## 接手后的优先实施

### P0：把自动补齐接进实际抓取链路

1. **重做推荐/核实任务的接续**。用户发起“推荐/抓取对标”后，只要当前账号浏览器可用、用户已登录且授权，候选落盘后自动继续核实；主页身份核实成功后，在**同一次浏览器占用**中采集头像、主页资料与最多 5 篇可见笔记，逐阶段落盘。若推荐阶段为了速度先做不访问浏览器的候选，后台也必须自动接续核实/观察，而非让用户逐卡点第二步。需要等待本人登录时，暂停该账号队列并显示具体阻塞原因；用户完成登录后可整体继续。
2. **agent 已经在 MCP/自带浏览器里抓取时就地记录**。调整提示词和任务合同，让 agent 在访问目标主页的同一轮，完成身份核对、头像元素局部截图（工具支持时）、主页字段与每篇笔记的观察检查点；不要关闭当前浏览器后再排一个相同账号的 worker 任务重复访问。`candidate → verified → observation` 每阶段完成即保存，不能只在最终回答里描述“看到了”。若 agent 不能写截图，只报告缺失/部分完成，不伪装成页面截图。现有 `playbooks/benchmark.md` 的推荐与观察两个章节需要合并成自动接续的操作顺序。
3. **服务端做可靠编排，不能只靠一段提示词**。在 `server/server.mjs` / `server/bridge.mjs` 与检查点合并边界增加按账号串行、可恢复的待采集队列/状态；核实结果写入后识别缺失观察并调度后续任务，但若当前 agent 正在同账号浏览器中采集，要等待其检查点/结束再判断，避免 worker 和 MCP 抢同一 profile。对同一个对标 ID 去重，避免 SSE、文件监听、重启重放重复派单。数据任务和采集任务的完成状态分开，不把“账号已核实”误报成“头像和笔记都抓完”。推荐任务在 worker 关闭时仍应自动走 agent 的浏览器/检查点路径；浏览器能力也不可用时准确显示阻塞，而不是暗中标记完成。
4. **旧数据补齐**。提供一个账号级“补齐缺失的已登记对标”动作（或启用自动采集时的一次性待办队列），筛选缺头像/主页观察/笔记观察的条目，按账号和对标逐条有界处理；不要求用户打开 6 张卡各点一次。中断后只重试未完成项，保留已有有效字段和时间，列表显示待办数、当前进度、失败原因及继续入口。不要在用户未准备登录时静默大量打开页面。

### 采集边界与完成定义

- 身份：工作台账号与实时登录小红书号一致；目标主页 URL、小红书号与已核实目标一致。不能依据旧 `browser.json`、搜索摘要、昵称相同或远程头像 URL 猜测。缺少必要身份就停止该目标，保留先前数据并提示用户，而非要求用户手填每个抓取字段。
- 单目标上限：一个主页、主页可见的最多 5 个不同站内笔记链接；保守页面等待与总超时，禁止点赞/关注/评论/发布。验证码、异常访问或账号不一致时停止，由本人处理，不绕过风控、不自动切无头、不复制 Cookie 或删除锁文件。
- 头像：仅目标主页头像**元素的局部 PNG 截图**才标记“页面截图”，且先落盘再写检查点；截取失败不清旧图。手动头像只是可选回退，不是自动化成功的验收替代品。
- 状态：`verified` 只表示身份；`profile`/`partial`/`complete`/`unavailable` 表示观察阶段。至少记录本次尝试、实际成功的篇数、缺失字段/失败原因、每个字段的观察时间/来源；未见到的数值不填 `0`。若只有 2 篇实际可见，显示“2 篇可见并已处理”，不凭空补满 5；未拿到头像或笔记列表时不能把整个目标呈现为完整抓取。
- 失败恢复：任何一篇成功后立即写独立检查点，超时/取消/崩溃后保留；冲突写入 `rejected/`，不能覆盖旧有效观察或用户手填字段。保留原 `notes.json`、`report.md`、爆款雷达、新增/删除与跨账号隔离行为。

## 已有数据合同与代码入口

- 数据：`accounts/<账号id>/benchmarks/index.json` 是列表/手填与核实资料；`<对标id>/snapshot.json` 是经服务端校验的原始观察；`<对标id>/notes.json`、`report.md` 属 agent 拆解，不能混用。数据根目录默认 `~/XHS-Workbench`，可由 `XHS_WORKSPACE` 覆盖；不要把真实账号内容写进测试数据或文档。
- 检查点：`benchmarks/checkpoints/pending/<id>.candidate.json`、`<id>.verified.json`；worker 用 `<id>.observation.json` 并立即合并，agent 用 `<id>.observation-<8位小写十六进制批次>-<步骤0…6>.json` 防止中间步骤覆盖。具体 JSON 字段见 `xhs-workbench/playbooks/benchmark.md:148`；合并与头像校验见 `server/content.mjs:157`、`server/benchmark-observation.mjs:137`。服务端已处理文件移到 `applied/` 或 `rejected/`。
- UI 入口与问题点：`web/modules/benchmark.js:323-332`；任务验证/派发：`server/server.mjs:314-388`；worker 生命周期与持久化回调：`server/bridge.mjs:305-331`、`server/browser-worker.mjs:182`；列表与详情读取：`server/content.mjs:275-325`。设计背景见 `docs/background-browser.md`、`docs/benchmark-observation.md`、`docs/benchmark-recovery.md`。

## 验收条件（请接手者逐项演示，而不只跑 mock）

1. 在**隔离临时数据目录**发起一次推荐/抓取任务：用户只发起这一次操作，不再点任何单卡补齐；模拟已登录且页面能读时，从候选到已核实、真实头像截图、主页资料及可见笔记检查点自动接续，列表与详情随 SSE 更新。
2. worker 关闭、但 agent 有浏览器能力时：同一个 agent 浏览器任务写入主页与逐篇检查点；不强制用户开启后台 worker，也不对同一目标重复开浏览器。真实登录不可模拟为已核实。
3. 有 6 个已核实而无 `snapshot.json` 的旧条目：一次批量补齐，按账号串行、有进度和暂停/继续；中断在第 3 个时前两个保留、恢复不重采已完成项；重复通知/重启不生成重复任务。
4. 测试至少覆盖：账号不匹配/未登录/风控、目标冲突、页面只有 0～4 篇、头像截图失败、字段缺失、逐篇超时/取消、损坏检查点、同账号浏览器租约、多账号隔离，以及原发布/评论/雷达流程回归。运行 `npm test`、JS 语法检查、`git diff --check`。
5. 在**获得用户许可的真实小红书有头页面**核对头像元素和笔记选择器、详情的真实字段；未获许可或平台限制时如实标“未验证/部分失败”，不能用假页面的 67 个测试宣称真实抓取完成。Windows Edge 的焦点和最小化还需 Windows 真机验收。

## 开发纪律

当前工作树含本轮之前及本轮的大量未提交更改和新文件。**不要 `reset --hard`、清空数据目录、覆盖用户账号文件或为了测试直接批量访问真实账号。** 开发与测试用 `XHS_WORKSPACE` 指向临时目录；若需要重启用户当前工作台，先确认没有在途任务并遵守其权限决定。更新两份 README、中文 `docs/` 和 playbook，使文档描述的是**实际完成的自动链路**；不要只修改按钮文案。用户未要求提交、推送或打包。
