# 对标任务超时与检查点

## 目的

浏览器核实可能因登录、页面加载或长任务而超时。旧流程等所有账号采完才改 `benchmarks/index.json`，即使浏览器已看过页面，任务中止时列表仍为空。新流程把“已写入”与“任务已完成”分开：每条候选、每条已核实账号，以及后续主页/逐篇可见笔记观察都独立保存，超时不撤销已完成的检查点。

## 使用流程

1. 「让 agent 推荐对标账号」只做不需浏览器的候选阶段。每找到一个候选就写 `accounts/<id>/benchmarks/checkpoints/pending/<对标id>.candidate.json`；候选没有真实粉丝数和主页时留空，页面标“主页待核实”。无法确认具体账号时不登记类目占位为真实账号。
2. 候选检查点落盘后，服务自动接续可选后台有头组件（显式开启时）或 agent 打开有头浏览器、按 `playbooks/browser.md` 核对登录并寻找该账号。确认真实主页后立即写 `<对标id>.verified.json`，包含主页 URL、页面昵称和观察时间；仅记录实际看到的小红书号/粉丝数。每核实一个就写一个，不等全部完成。
3. 服务端把候选/核实检查点合并到 `index.json`，再把头像、主页与最多 5 篇可见笔记的观察检查点合并到单独 `snapshot.json`，页面实时刷新。任务超时/取消或服务重启后，已合并或已完整写完的检查点仍可见；推荐任务重试跳过已有/已核实账号，单账号资料补齐可继续刷新已核实账号。观察数据合同见 [竞品对标卡片与原始观察](benchmark-observation.md)。**未写入的浏览器观察无法恢复；若首条检查点前就超时，列表仍可能为空。**
4. 核实后再拆解或追踪；没有主页时也可以上传足够截图先做拆解，但不能把账号标为已核实或开启无链接追踪。拆解任务不再预先把账号标成 `analyzing`，避免超时后误显示为“拆解中”。

## 设计与取舍

- `candidate`、`verified` 与 `observation` 三类独立 JSON 文件；候选不是已核实事实，观察不是拆解报告。每个文件只涉及一个账号，可用 agent 已有的文件编辑能力，无需扩展 CLI 命令权限或增大推荐任务的 1800 秒超时；可选只读 worker 的单账号任务约 180 秒。
- 服务端在读取列表、任务结束/出错以及服务启动时扫描 `checkpoints/pending/`，校验文件结构、ID、HTTPS 小红书主页、昵称与观察时间；用 `store.writeJson` 原子写入合并结果。候选用 ID 去重，核实只关联已存在候选；不会覆盖用户现有备注、追踪开关、拆解状态和已填的粉丝数；页面观察到的粉丝数另存为 `observedFollowers`，冲突时界面同时显示“页面”和“手填”值。已处理检查点移到 `applied/`；无法合并的放到 `rejected/`，原因在同名 `.reason.txt`，页面显示数量。未写完的 JSON 留在 `pending/`，绝不当作空数据。用户删除的账号 ID 记在 `deleted.json`，旧检查点不能将其恢复。
- 任务超时仍在对话里标记为错误，不伪装成成功；不会从流式文字、工具记录或页面快照猜出粉丝数。文件确认写完之前不能保证保留任何进度；平台登录/风控仍需用户本人处理。

## 验证

`npm test` 覆盖：候选与核实信息合并、用户字段保护、重复回放、冲突和残缺文件、账号隔离、删除防复活；假 agent 写完一条后故意超时，检查真实 HTTP 服务的对话错误、页面 API 列表以及重启后保留的结果。真实小红书账号的核实需要用户登录且不在自动化测试中执行。
