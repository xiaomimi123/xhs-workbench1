# 数据复盘操作手册

> **中枢技能**：xhs-review（数据复盘）——公司统一的业务标准，做这件事之前先用 `read_skill` 读；读不到（没接中枢、没权限、失败）就只按本手册做，不要重试。优先级见 `README.md`「与中枢技能的分工」。

**操作网页前先按 `browser.md` 完成登录检查和账号核对。**

目标：定期记录数据，找出"什么有效、什么无效"，把结论写回知识库，指导下一轮选题和创作。

## 数据位置

当前账号数据目录下 `analytics/`：

```
analytics/
├── notes.json      每篇笔记的最新数据 + 历史快照
├── account.json    账号级每日数据
├── reports/        复盘报告（Markdown）
└── imports/        用户上传的导出表格 / 截图（只读）
```

### notes.json

```json
{
  "updatedAt": "2026-10-15T09:00:00.000Z",
  "items": [
    {
      "id": "a_xxx",
      "noteId": "n_xxx",
      "title": "笔记标题",
      "url": "笔记链接",
      "publishedAt": "2026-10-10",
      "metrics": { "views": 12000, "likes": 830, "collects": 560, "comments": 42, "shares": 18, "follows": 25 },
      "history": [
        { "date": "2026-10-14", "views": 9800, "likes": 700, "collects": 480, "comments": 35, "shares": 15, "follows": 20 },
        { "date": "2026-10-15", "views": 12000, "likes": 830, "collects": 560, "comments": 42, "shares": 18, "follows": 25 }
      ]
    }
  ]
}
```

- `metrics` 是最新累计值；`history` 每天最多一条（同一天重复抓取就覆盖当天那条），日期格式 `YYYY-MM-DD`。
- 数字尽量写成数值；页面显示"1.2万"时可以原样写字符串，工作台能识别。
- `noteId`：如果能和工作台里的笔记对应上（看 `notes/*/meta.json` 的 `publishedUrl` 或标题），就填上。
- 新笔记追加条目，`id` 用 `a_` + 任意字母数字；不要删除旧笔记。

### account.json

```json
{ "history": [ { "date": "2026-10-15", "followers": 5230, "views": 45000, "likes": 3100, "collects": 2200, "comments": 180 } ] }
```

每天一条，同一天覆盖。字段拿不到就省略。

- `followers` 是当天的**粉丝总数**；`views`、`likes`、`collects`、`comments`、`follows` 是**当天新增**（创作者中心「账号概览」按日给出的数字）。
- 工作台的「每日趋势」图直接画这些值。

## 抓取数据

1. 用浏览器控制工具打开创作者中心的数据中心 / 笔记管理页面（未登录时请用户登录，规则同 `publish.md`）。只读取，不做任何修改操作。
2. 读取近 30 天发布的笔记数据和账号总览数据，更新 `notes.json`、`account.json`。
3. 没有浏览器能力时：读取 `imports/` 里用户上传的导出表格（CSV / Excel）或截图来整理；都没有就告诉用户如何从创作者中心导出数据并上传。
4. 拿不到的数据留空，不要估算或编造。
5. 回复用户：更新了多少篇、数据最好和最差的笔记各是什么。

## 首次导入历史笔记

工作台是新装的、但账号里已经发过笔记时，把历史笔记导入数据复盘，让指标和排行立刻有内容。按 `url` 判断，已有条目跳过。

1. 打开创作者中心「笔记管理」，逐页慢速读取（只读取，不修改任何东西），尽量多翻几页。
2. 对每篇笔记，在 `notes.json` 里**追加**条目：
   - `id`（a_ + 随机字母数字）、`title`、`url`、`publishedAt`、`metrics`（当前累计值）
   - `history` 写一条当天快照（`date` 填今天）
   - `imported: true`（标记这是导入的历史笔记）
3. 链接能和工作台里笔记 `meta.json` 的 `publishedUrl` 对上的，照常填 `noteId`。
4. 回复用户：导入了多少篇、最早到最近的时间跨度。

- 导入的笔记只有当天一次快照，看不到历史趋势是正常的；之后每天定时抓取会开始积累。
- 没有浏览器能力时：告诉用户可以从创作者中心导出数据表格，上传到 `analytics/imports/`，然后按「抓取数据」一节的方式从 imports 整理。

## 写复盘报告

保存到 `reports/YYYY-MM-DD-<主题>.md`，例如 `2026-10-15-周复盘.md`：

```markdown
# 周复盘：10/09 - 10/15

## 数据概览
本周发布 N 篇，阅读 / 点赞 / 收藏 / 涨粉，与上周对比

## 表现最好的笔记
| 笔记 | 阅读 | 互动率 | 为什么好 |

## 表现不佳的笔记
| 笔记 | 阅读 | 互动率 | 可能的问题 |

## 结论
- 继续做：
- 停止做：
- 尝试做：

## 下周行动
1. 具体、可执行……
```

- 互动率 = (点赞 + 收藏 + 评论) / 阅读。
- 分析要结合选题（`topics/`）、标题、封面（`notes/`）和发布时间，不只看数字。
- 写完后按 `knowledge.md` 把"继续做 / 停止做"的结论沉淀到知识库 `复盘结论/`，已有相近结论就补充或修正。

## 沉淀到公司知识库「复盘总结」（接入企业中枢时）

复盘报告只在本机。值得全公司共享的经验，要沉淀到中枢的「复盘总结」知识库，让别的同事和他们的 agent 也能查到。**由你建议、由用户确认、再由主管审核**，三步都不能省：

1. **提炼候选**：复盘报告写完后，从「结论」里挑 1–3 条值得沉淀的（继续做 / 停止做 / 尝试做），每条都要有**数据依据**（具体指标、对比、样本范围），没有依据的不要提。账号数据（阅读、点赞、收藏、评论数、涨粉等）可以写进去，这是判断运营做得好不好的直观依据。
2. **问用户确认**：在回复里列出候选，逐条问「要不要沉淀到公司知识库『复盘总结』？」，**等用户明确说要**。用户没回应、说不要、或只是说「好的复盘不错」，都不提交。
3. **提交建议**：用户确认后，调用中枢工具 `propose_improvement`：`kind` 填 `new_doc`，`knowledge_base` 填「复盘总结」，`target` 填文档名（如 `2026-10 第 3 周 小红书运营复盘`），`summary` 一句话说明沉淀什么，`rationale` 写为什么值得共享，`proposed_content` 写完整的 Markdown 文档（格式见下）。提交后告诉用户建议编号，说明要由主管审核后才会入库；之后可用 `my_proposals` 查结果。

文档格式：

```markdown
# 2026-10 第 3 周 小红书运营复盘

> 来源：<账号名>，数据范围：10/09–10/15，整理人：<用户>

## 数据依据
本周发布 N 篇，阅读 / 点赞 / 收藏 / 涨粉，与上周对比；最好和最差的笔记各是哪篇、互动率多少

## 经验结论
- 继续做：……（依据：……）
- 停止做：……（依据：……）
- 尝试做：……（假设：……）
```

不要这样做：

- **未经用户确认不提交**。定时 / 自动任务（用户不在）里不提交，只在复盘报告里标出「建议沉淀」的结论，等用户回来再问。
- 不放评论、私信里**其他用户的昵称、联系方式或原话**，不放登录凭证、密钥，不放与运营无关的个人隐私。
- 同一条结论不要重复提交；`propose_improvement` 提示「已经有一条待处理」时，告诉用户等主管处理。
- 没有中枢工具（没接中枢、没有权限、调用失败）时，不重试，告诉用户「这次没能提交，结论已存在本地知识库」，并照常按上面「写完后沉淀到本地知识库」处理。
