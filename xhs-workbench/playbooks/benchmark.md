# 竞品对标操作手册

> **中枢技能**：xhs-breakdown（爆款笔记拆解）——公司统一的业务标准，做这件事之前先用 `read_skill` 读；读不到（没接中枢、没权限、失败）就只按本手册做，不要重试。优先级见 `README.md`「与中枢技能的分工」。

目标：找到值得学习的账号，拆出它们**可复制的规律**，变成我方的选题和方法论。

## 数据位置（当前账号数据目录下）

```
benchmarks/
├── index.json                 对标账号列表
└── <对标id>/
    ├── report.md              拆解报告（Markdown）
    ├── notes.json             agent 拆解/雷达笔记（与页面观察分开）
    ├── snapshot.json          已校验的主页和最多 5 篇笔记原始观察
    ├── avatar-captured-*.png  头像元素的局部截图（若采集成功）
    └── screenshots/           用户上传的截图（只读，可分析）
benchmarks/checkpoints/
├── pending/                  agent 逐条写入检查点；服务端自动合并
├── applied/                  已合并的检查点
└── rejected/                 冲突与错误检查点及 .reason.txt
```

### index.json

```json
{
  "items": [
    {
      "id": "b_xxx",
      "name": "账号名",
      "xhsId": "小红书号",
      "url": "主页链接",
      "followers": "12.3万",
      "positioning": "一句话定位",
      "remark": "用户备注",
      "status": "pending | analyzing | analyzed",
      "analyzedAt": "2026-10-15T10:00:00.000Z",
      "summary": "一句话总结最值得学的点（显示在卡片上）",
      "tracking": true,
      "lastCheckedAt": "2026-10-15T10:00:00.000Z",
      "newCount": 2,
      "radarNote": "新笔记《标题》点赞 1.5万，可能爆了：https://…"
    }
  ]
}
```

- 新增对标账号：`id` 用 `b_` + 任意字母数字（如 `b_20261015a`），`status` 填 `pending`。
- 修改时保留其他字段，只改需要的字段；不要删除条目（用户可以在界面删除）。
- `tracking` 由用户在界面开启，表示希望定期检查这个账号的新笔记；`lastCheckedAt`、`newCount`、`radarNote` 只在「追踪检查」（见下文）时由你更新。

### notes.json

数组，每篇笔记一项；仅使用已导入或明确启动后采集的资料，不额外访问页面：

```json
[
  {
    "title": "笔记标题",
    "url": "笔记链接",
    "type": "图文 | 视频",
    "likes": "1.2万",
    "collects": "8000",
    "comments": "320",
    "publishedAt": "2026-09-01",
    "coverText": "封面上的文字",
    "topicType": "选题类型，如 清单/教程/测评/避坑/经验分享",
    "titlePattern": "标题套路，如 数字+痛点、反常识",
    "firstSeenAt": "2026-10-15T10:00:00.000Z"
  }
]
```

- `firstSeenAt` 是这篇笔记第一次被采集的时间：初始拆解时不用写；「追踪检查」新发现的笔记必须写。

## 拆解步骤

1. 先确认目标账号的身份（已核实主页，或有足够截图材料）。**不要在开始时把状态改成 `analyzing`**，否则任务超时会一直显示“拆解中”；资料不足时保持 `pending`，已有旧的 `analyzing` 状态也改回 `pending`。
2. 收集信息，按能力从高到低选择方式：
   - 使用本地 snapshot.json、notes.json 和用户截图。缺资料时说明缺项，不自行打开浏览器。
   - 能搜索网页：搜索账号名和代表作，收集公开信息。
   - 都不能：读取 `screenshots/` 里用户上传的截图；截图不够时，在回复里告诉用户需要截哪些页面。
3. 写 `notes.json`。
4. 写 `report.md`，结构如下：

```markdown
# 对标拆解：@账号名

> 一句话结论：最值得学的是……

## 账号画像
定位、目标人群、人设、更新频率、变现方式

## 爆款规律
### 选题
### 标题
### 封面
### 正文结构
### 评论区运营

## 数据观察
互动最高的几类内容，以及可能的原因

## 我们可以借鉴的 5 件事
1. 具体、可执行的动作……

## 不建议照搬的地方
```

5. 更新 `index.json`：`status` 改 `analyzed`，写 `analyzedAt` 和 `summary`，补上 `followers`、`positioning` 等字段。
6. 回复用户：3-5 条最重要的发现，并建议下一步（生成选题 / 沉淀知识库）。

## 推荐对标账号

推荐只登记候选待办，不启动浏览器。用户独立核对登录账号，再明确启动一次只读采集，才允许由工作台 worker 保存头像、主页与最多五篇笔记。以下检查点合同用于持久化已授权观察，不构成自动浏览授权。

**第一步（候选先落盘）**：根据账号定位（见提示词中的「当前账号」和知识库 `账号定位/`）给出 5-8 个候选。**每想到一个就先写一个完整的 JSON 文件**到 `benchmarks/checkpoints/pending/<id>.candidate.json`，再继续下一条；`id` 为 `b_` + 当前时间标识 + 随机字母数字，先查现有列表避免冲突；下面的 id 只是示例，不要照抄。文件内容例如：

```json
{ "stage": "candidate", "id": "b_20261017a", "name": "待核实账号名", "remark": "候选理由及搜索线索（未经核实）" }
```

候选不是已确认的小红书账号；不要写猜测的主页、粉丝数、小红书号，也不要开启追踪。找不到真实账号名时不要把“某某类·待核实”当作账号登记；不足 5 个就如实给出已找到的数量。候选保存后停止，不自动核实或打开浏览器。已在 `index.json` 中的候选不要重复登记。

**明确启动后**：只读 worker 使用同一存活浏览器会话中的有时效账号核对结果，缺少结果时停止并提示独立核对。不得自动改用 agent 浏览器绕过访问锁。每完成一阶段立即写独立 JSON 检查点，示例：

```json
{
  "stage": "verified", "id": "b_20261017a",
  "url": "https://www.xiaohongshu.com/user/profile/0123456789abcdef",
  "profileName": "主页显示的昵称", "xhsId": "页面显示的小红书号",
  "followers": "页面显示的粉丝数", "observedAt": "2026-10-17T05:00:00.000Z"
}
```

只填**实际看到**的字段，没看到的 `xhsId` / `followers` 留空；后台组件会附 `source: "profile-visible"`，服务端只记录主页 URL 和字段名，不保存页面快照；`url`、`profileName` 和实际核实时间必填。原候选与主页不符时不要强行关联，应说明疑点并重新找真实账号。先已有候选 id，才能写核实检查点；新发现的账号先写候选，再写核实。每完成一个向用户报告一个；登录失效按 `browser.md` 处理（最多等待 5 分钟）。已完整观察的条目跳过；仅已核实而缺观察的条目仍需补齐，保留已有效落盘的字段。

**超时 / 取消恢复**：完整写入的检查点会在列表读取时及任务结束时合并并保留；未写完的 JSON 不会当成结果，没写入的浏览器观察也无法自动恢复。重试时先读 `index.json`，推荐任务跳过已有/已核实账号；单账号资料补齐任务可以重新读取已核实账号。无法合并的检查点在 `checkpoints/rejected/`，原因在同名 `.reason.txt`，不凭猜测修复冲突。`checkpoints/` 由服务端管理，勿手工删除已处理文件。

## 主页资料与近 5 篇笔记观察

这一流程为「竞品对标」卡片补真实头像、主页字段和主页**可见的前 5 篇笔记**；不是按时间排序的“最新 5 篇”，也不是爆款/规律拆解。结构化原始观察最终由工作台写到 `<对标id>/snapshot.json`，不要直接编辑该文件，更不要把它当作 `notes.json`、`report.md` 或已拆解结论。后台有头组件开启且兼容时由确定性读取器完成，**不调用模型读取字段**；未开启或点「改用 agent」时按以下相同合同完成。

1. **先核对登录和目标身份**：遵守 `browser.md`；当前工作台账号的小红书号必须已填写且与此刻登录的账号一致。目标主页应为 `https://www.xiaohongshu.com/user/profile/<id>`；逐字核对页面昵称、小红书号与 `index.json` 中的记录。未核实则按上节先写 `<id>.verified.json`，让工作台合并后再写观察；已有核实则仍需重新打开主页核实身份。若主页、账号、小红书号不一致或出现登录/验证码/访问限制，停止，不写假数据；旧观察保持原样。不能靠搜索摘要、缓存、旧 `browser.json` 或头像猜身份。
2. **主页先落盘（混合采集）**：身份仍以实时主页 URL、小红书号核对。头像优先下载**目标头像元素实际 currentSrc**，只允许 HTTPS 小红书图片 CDN，最多 2MB，PNG/JPEG/WebP，保存 `avatar-download-<16位小写十六进制>.<扩展名>`，检查点 `avatarFile` 填文件名，界面标记“原图下载”。下载失败才截该头像元素，使用 `avatar-source-<16位小写十六进制>.png`，标记“页面截图”。不得猜 URL 或下载其他作者头像。主页资料截可见资料区域并在本机 OCR，保留截图与识别原文，再与可见 DOM 标签交叉核对，无法核对的字段省略并说明。通过 server/benchmark-observation.mjs 的 `stageVisualEvidence(accountId,id,{png,ocr})` 写证据，返回值填 `profileEvidence`；OCR 可使用 server/visual-capture.mjs 的 `recognizeScreenshot(png)`（macOS Vision）。工具不可用时保留已经得到的数据，标记 partial，不冒充完成。
3. **逐篇读取逐篇落盘**：从主页当前可见列表取最多 5 个不同的站内笔记链接，只接受 HTTPS 小红书 `/explore/<id>` 或 `/discovery/item/<id>`；必须点击主页上该笔记的可见卡片进入，不能拼接或直接导航缺少参数的链接（用 WorkBuddy 浏览器插件的只读档时没有点击工具：改用 `tab_goto` 打开该卡片链接的**原文**，带着 `xsec_token` 等全部参数，等同于点进去；仍然不许自己拼接或删参数）。打开每篇后核对 URL，保存可见标题、简介、发布时间原文、图文/视频、点赞/收藏/评论。没有看到的字段**不写**，绝不猜零或把同一页的其他计数填进来。记录的是主页展示顺序 `position`（从 0 开始），不是时间顺序；只浏览这些页面，不自动翻页/无限滚动。遇风控/验证码立即停止，不重试绕过。每读完一篇就写一个独立检查点，不等全部结束。先前写完的文件可在超时/重启后恢复。
4. **收尾**：头像原图下载或元素截图成功、主页截图和 OCR 完成且有核对字段、笔记列表已看到（可为零篇）、全部可见笔记实际读完且没有缺失流程时写 `state: "complete"`；一部分读不到写 `partial` 并给具体原因；无可读列表写 `unavailable` 并说明原因。`complete` 不意味着每个互动字段都存在。未观察到的数字留空；报告如需规律分析仍要另行完成拆解。发现账号信息中途被改动或检查点进入 `rejected/` 时停止并读同名 `.reason.txt`，不能覆盖已有文件或强行续写。

**检查点格式**：每轮为该目标生成一个不同的 8 位小写十六进制批次号（例如当前 UNIX 秒的十六进制表示，勿照抄例子）；逐步写到 `benchmarks/checkpoints/pending/<id>.observation-<批次>-<步骤>.json`：主页为 `0`，笔记依次为 `1`～`5`，收尾为 `6`。步骤号只占一位、同一批次不得重复；建议先写同目录临时文件，再原子重命名为 `.json`，避免服务读取半成品。服务按 id、阶段、文件名排序合并；每份 JSON 都写完整身份字段。服务会把已处理文件移至 `applied/` 或 `rejected/`，不要手动移走。下一轮换新批次号，不能覆盖仍在 `pending/` 的结果。

主页示例（填入**真实观察值**；`source` 固定 `agent-visible`）：

```json
{
  "stage": "observation", "id": "b_20261017a",
  "url": "https://www.xiaohongshu.com/user/profile/0123456789abcdef",
  "xhsId": "页面显示的小红书号", "profileName": "页面显示的昵称",
  "observedAt": "2026-10-17T05:00:00.000Z", "source": "agent-visible",
  "state": "profile", "reason": "头像元素无法局部截图",
  "profile": { "bio": "页面可见简介", "followers": "12.3万", "following": "42", "likesAndCollects": "8.6万" },
  "discoveredCount": 3
}
```

若截图成功，再附 `"avatarFile": "avatar-source-0123456789abcdef.png"`；`noteCount` 仅为主页明示的**总笔记数**，不是本次读到的篇数，可在 `profile` 里补。第二份文件（步骤 `1`）只写第一篇实际读到的笔记与累计尝试数；后续逐篇类推，无需重复 `profile`：

```json
{
  "stage": "observation", "id": "b_20261017a",
  "url": "https://www.xiaohongshu.com/user/profile/0123456789abcdef",
  "xhsId": "页面显示的小红书号", "profileName": "页面显示的昵称",
  "observedAt": "2026-10-17T05:01:00.000Z", "source": "agent-visible",
  "state": "profile", "attemptedCount": 1,
  "notes": [{ "url": "https://www.xiaohongshu.com/explore/0123456789abcdef", "position": 0,
    "title": "页面实际显示的标题", "type": "图文", "likes": "15", "publishedAt": "3天前" }]
}
```

收尾文件（步骤 `6`）带 `state: "complete" | "partial" | "unavailable"`、`reason`、实际累计 `attemptedCount`（0～5）；`profile`/`notes`/`avatarFile` 可省略，之前已存的字段和时间不会被冒充为本轮新数据。服务对每份检查点校验 id、主页 URL、小红书号、时间、字段长度、笔记链接/去重、数量和 PNG；冲突拒绝并保留之前的有效数据。前端详情「主页数据」展示各字段来源/时间；头像文件只是页面图像，不证明账号身份。旧条目和旧报告不会自动拥有头像或五篇笔记。

## 追踪检查（爆款雷达）

后台只读组件可手动**刷新已登记主页及其最多 5 篇可见笔记的原始字段**，但不判断哪篇是新笔记或爆款，不修改 `notes.json`；追踪到点仅提醒，分析使用本地资料。

开启追踪（`tracking` 为 true）只产生定时提醒。用户明确采集后，对本地新观察执行：

1. 读取已保存的主页观察及笔记；不自动打开主页，不把可见顺序称为最新顺序。
2. 对照该账号 `notes.json` 里已有的 `url`，把**没有出现过**的笔记追加为新条目，写上 `firstSeenAt`（当前时间）；已有条目只更新互动数据，不要改标题等其他字段。没有新笔记就不动文件。
3. 更新 `index.json` 里该账号的三个字段：
   - `newCount`：本次新发现的笔记数；
   - `radarNote`：某篇新笔记的点赞数超过阈值（`automation.json` 里 `radar.likesThreshold`，默认 1000）时，写一句「标题 + 点赞数 + 链接」；没有超的就删掉这个字段；
   - `lastCheckedAt`：当前时间。
4. 回复用户：每个账号发现了几篇新笔记、有没有疑似爆款、建议跟拍还是只观察。

**没有浏览器能力时**：直接回复说明这次无法检查，不要编造笔记数据，也不要更新 `lastCheckedAt`。

## 原则

- 只学规律，不抄内容；报告中不要大段复制对方原文。
- 数据拿不到就留空，不要编造。

## 待办与访问锁

候选/核实检查点只登记未授权待办。明确启动仅授权当前待办，本次启动后新到的候选不自动执行；每次尝试后消耗授权。中断或重启保留已有资料，并暂停待办。

账号级访问锁保存于 browser-access.json，覆盖工作台队列、手动核实与派发的浏览器任务。暂停立即取消该账号排队及运行任务；登录、验证码或平台限制停止并保存原因。普通恢复不解除平台限制；限制解除须由用户在独立入口确认，且不自动启动任务。不要手工修改锁文件。

独立核对账号后才能启动采集。笔记间以页面就绪条件等待，辅以有界随机间隔；通过详情关闭或历史返回原主页，返回失败停止。随机等待仅控制请求节奏，不保证免风控。
