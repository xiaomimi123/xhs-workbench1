## v0.8.18（2026-10-28）新增浏览器方式「ego lite 浏览器」（实验）

来源：用户想试 ego lite（专为 AI agent 做的浏览器）代替 WorkBuddy 浏览器插件，这样员工不用再装 WorkBuddy。

- **「连接与设置」里多一个浏览器方式「ego lite 浏览器（实验）」**：本机装了 ego lite（找 `ego-browser`：环境变量 `EGO_BROWSER_BIN` → `~/.local/share/ego/active_version_dir/` → `~/.local/bin` → PATH）才可选，没装时说明怎么装；选择时先做连接测试，通过才保存。目前只能配合 CodeBuddy，没有测试档
- **只读由固定工具保证**：CodeBuddy 通过工作台自带的 MCP 小服务 `ego-reader`（随包：`xhs-workbench/ego-reader/server.mjs`，源头在中枢仓库 `tools/ego-reader`）读小红书，只有 4 个只读工具：`xhs_check_login`、`xhs_read_me`、`xhs_read_feed`、`xhs_read_note`；没有点击 / 输入 / 打开任意网址 / 执行脚本的能力（`ego-browser nodejs` 本身能执行任意 JS，所以不能把 agent 写的脚本交给它）。工作台为账号生成 `config/mcp/<账号>.ego.json`，只放行 `mcp__ego-reader`，不带禁用工具列表。保护：两次读取至少间隔 20 秒、每小时最多 12 次、停止文件 `run/ego-reader.STOP`
- **登录判断只认页面状态**：`window.__INITIAL_STATE__.user.loggedIn / userInfo.guest`。小红书游客也能看信息流和笔记，**不能**用「找不到登录按钮」判断（我们就因此把游客误判成已登录过）。`xhs_read_me` 未登录时只返回 `loggedIn:false`，已登录才用页面状态里的 userId 和 xsecToken 打开自己的主页，读昵称、小红书号、IP、简介、标签、关注 / 粉丝 / 获赞、可见笔记标题
- **账号管理「在浏览器登录」按引擎走不同提示词**：ego 方式只调用一次 `xhs_read_me`：未登录就写 `browser.json` 为 `loggedIn:false` 并让员工自己在 ego lite 里扫码，不继续、不替员工登录；已登录才写 `browser.json` 和 `profile-suggestion.json`（0.8.17 起的自动填定位 / 人群 / 风格）。`playbooks/browser.md` 新增「ego lite 浏览器方式」一节
- **范围**：目前只覆盖账号管理的登录核对和主页分析；竞品对标采集、批量采集仍只支持 WorkBuddy 插件方式（选了 ego 时竞品对标页会说明）
- **验证**：`ego-engine.test.mjs` 7 项（检测顺序、MCP 配置、CodeBuddy 参数、选择时的各种失败、无测试档、网页选项、ego 提示词）；原来一条按旧报错文字断言的测试已更新（行为不变，仍拒绝 chrome 等未知方式）；全量 460 通过，2 个失败是本机没装 ffmpeg 的已知项；ego-reader 自身 24 项校验 / 保护测试（中枢仓库 `tools/ego-reader/test.mjs`）
- **没验证**：① **真实的 CodeBuddy → ego-reader → ego lite 整条链**（开发机上的 CodeBuddy 没登录，只在测试里覆盖了 MCP 握手和工具；需要在虚拟机里验证）；② `xhs_read_me` 在**真实已登录**页面上的选择器（昵称、小红书号、简介等用的是常见结构加文字模式兜底，未登录时无法验证，已登录后才能确认）；③ 登录态是否在 ego lite 的不同窗口 / 任务空间之间共享；④ 员工机上 ego lite 的安装、首次设置、PATH
- 本机之前对 ego lite 的「已登录」判断是错的（实为游客），已在中枢仓库 CHANGELOG 更正

## v0.8.17（2026-10-28）在浏览器登录时顺带分析账号，自动填好定位 / 人群 / 风格

来源：用户说明正常流程应该是——通过浏览器登录核对的时候，就分析账号并自动填好账号管理里的定位、目标人群、内容风格。否则竞品对标推荐时因为这些都是空的，一个候选也登记不出来。

- **提示词分两步**（都只读）：一、登录核对并写 `browser.json`（0.8.16 起）；二、已登录时，在页面里找到「我」的入口，用打开链接原文的方式只读打开**自己的主页**（只看这一页：不点开笔记详情、不翻页、不关注 / 点赞 / 收藏 / 评论 / 私信），按主页上实际看到的简介、标签和可见笔记标题，各写一句定位 / 人群 / 风格（≤60 字，看不出来留空、不编造），写入 `accounts/<账号 id>/profile-suggestion.json`。没登录就跳过。操作手册 `playbooks/browser.md` 新增「登录后分析自己的账号」一节与之对应
- **服务端校验后再填**（新模块 `server/profile-suggestion.mjs`，监听该文件）：agent 不直接改 `config/accounts.json`。主页上的文字是不可信输入，之后会进入给 agent 的提示词，所以统一过滤：只收字符串、去掉尖括号 / 反引号 / 花括号 / 方括号 / 反斜杠和控制字符（含 U+2028/2029）、折成单行、限长 80；**只填账号里还是空的字段**，用户已填的不覆盖；写回 `appliedAt / applied / skipped`，同一份建议不会重复套用；文件没写完整（不是完整 JSON）时什么都不做，等下一次变化
- **界面**：套用后账号管理页自动刷新，账号卡片下注明「定位、目标人群由 agent 根据你的主页分析填入（时间），不准可以点编辑修改」
- **顺带发现并修了一个坑**：`store.getAccount(id)` 对不存在的 id 会回退成默认账号，新模块一开始用了它，会拿错账号的字段判断「是否已填」；改为严格按 id 查找（测试抓到的）
- **验证**：`profile-suggestion.test.mjs` 6 项（只填空字段不覆盖、过滤标记和控制字符和限长、文件没写完整、非法 / 不存在的账号 id、建议全空、服务端接线）；`login-check.test.mjs` 更新；全量 453 通过，2 个失败是本机没装 ffmpeg 的已知项；**真实服务端到端**（临时数据目录起服务 → 创建账号 → 写建议文件 → 监听套用 → `GET /api/accounts` 看到定位 / 人群、风格没被覆盖、第二次建议也不覆盖）7 项通过
- **没验证**：虚拟机里 agent 真实读主页并写出文件（依赖 WorkBuddy 浏览器插件、CodeBuddy 的文件编辑权限，以及它能否找到「我」的入口链接）；分析出的定位准不准；这一步读自己主页算一次额外的页面访问，目前**不经过**采集节奏闸门（总开关 / 每日上限），只有一页、只读，若要计入额度需另行设计

## v0.8.16（2026-10-28）登录核对的结果要存下来；账号可一键填入小红书号

来源：虚拟机里验证 0.8.15：在账号管理点「在浏览器登录」，agent 核对成功（已登录、昵称、小红书号都读到了），但刷新页面后账号管理仍显示「小红书号 未填写 / 尚未保存登录记录」。

- **原因**：操作手册 `playbooks/browser.md`「登录检查」第 5 步规定 agent 把结果写进账号数据目录的 `browser.json`，账号管理页的「上次已登录 · 昵称 · 小红书号」就读它。但「在浏览器登录」发给 agent 的那句话只写了「把结果告诉我」，agent 照做，结果只留在对话里，刷新就没了。0.8.11 起登录核对不再走后台浏览器（`onBrowserPrepared` 只给已停用的 Playwright 路径用），这条 agent 路径一直没有保存
- **改法**：提示词明确要求按手册「登录检查」把 `loggedIn / nickname / xhsId / checkedAt` 写进 `accounts/<账号 id>/browser.json`（没登录就写 `loggedIn: false`），**只许写这一个文件**，其余约束不变（不打开对标主页、不读笔记、不发布）。写入后服务端的文件监听会推送 `browser` 变更，账号管理页自动刷新
- **一键填入小红书号**：账号信息里没填小红书号、而上次核对已登录且读到了号时，账号卡片上出现「把 xxx 填为这个账号的小红书号」按钮（用户点了才填，只提交 `id` 和 `xhsId`，不覆盖已填的号）。填了号以后，自动操作才会做「登录的号与账号一致」检查
- **关于「竞品对标要再登录一遍」**：不是数据没传过去。手册规定每次操作前都**实时**核对当前登录的号（`browser.json` 只是上一次的记录，登录状态随时可能变）；小红书的登录态本身在你自己的浏览器里，不需要重新扫码。竞品对标页现在没有数据，是因为还没添加对标账号
- **验证**：`login-check.test.mjs` 增加到 8 项（提示词含 `browser.json` 路径、手册、四个字段和「只写这个文件」；一键填入只在已登录、读到号、账号没填号时提交，不覆盖已填的号；按钮显示条件和事件分发），`account-xhsid.test.mjs` 2 项（只更新小红书号、账号不存在返回 404）；全量 447 通过，2 个失败是本机没装 ffmpeg 的已知项
- **没验证**：虚拟机里的真实流程（agent 是否真的写出 `browser.json`、页面是否自动刷新、按钮能否点）；agent 写文件依赖 CodeBuddy 的 `acceptEdits` 权限模式（适配器里已配置，但没单独验证这一次写入）

## v0.8.15（2026-10-28）「在浏览器登录」不再指向一个不存在的按钮

来源：虚拟机里测 WorkBuddy 插件路线时，用户反馈：账号管理页点「在浏览器登录」提示「请先在你自己的浏览器里登录小红书，再到『竞品对标』页点『先核对登录账号』」，但竞品对标页里没有这个按钮，账号也就没法登录核对。

- **原因**：「先核对登录账号」按钮在「补齐对标资料」卡片里，而这张卡片在**没有任何对标账号**时整张不显示（`benchmark.js` 里 `!V.items.length && !items.length && kind === 'open'` 直接返回空）。新用户一定没有对标账号，所以一定找不到按钮
- **改法**：① 账号管理页的「在浏览器登录」直接发起核对（agent 在员工自己的浏览器里只读一页，比对当前登录的号），不再让用户去别的页面找；核对逻辑抽成 `checkLoginAccount()`，两处共用；② 竞品对标的空状态里也加了「先核对登录账号」按钮和一句说明；浏览器方式不是 WorkBuddy 插件时仍提示去「连接与设置」选
- **验证**：`tests/login-check.test.mjs` 4 项（插件模式直接发起且提示词不含对标主页 / 发布；非插件模式只提示不发起；账号页调用共用函数；空状态有按钮）
- **没验证**：在虚拟机里点一遍真实流程（需要 WorkBuddy 插件和已登录的 Edge）；agent 实际读页、比对的结果

## v0.8.14（2026-10-28）启动 CodeBuddy 前把 WorkBuddy 的环境洗干净

来源：员工电脑上 CLI 登录失败的根因复核。同一台机器上，最小环境运行 `codebuddy -p` 连续 5 次以上都成功，在 WorkBuddy 会话环境里连续 5 次以上都是 Authentication required——决定成败的是进程所处的环境，不是凭据。

- **`sanitizeAgentEnv` 补清 WorkBuddy 的 shim 钩子**：沙箱里一律去掉 `NODE_OPTIONS` / `PYTHONPATH` / `PYTHONSTARTUP` / `BASH_ENV` / `ENV` / `EXEPATH` / `ACC_PRODUCT_CONFIG*`；取值指向 workbuddy 目录的其他变量也去掉；`PATH` 只剔除 workbuddy 的目录。以前只清 `WORKBUDDY_*` / `CODEBUDDY_*` 和回环代理，这些钩子仍把 CLI 留在「WorkBuddy 上下文」里
- **判定「被 WorkBuddy 拉起」更宽**：除了有 `WORKBUDDY_*`，`NODE_OPTIONS` 等钩子变量指向 workbuddy 目录也算；没有任何痕迹时，用户自己的 `NODE_OPTIONS` / `PYTHONPATH` 不动
- **没有改成完全白名单**：全白名单会误伤员工自己的代理、证书和 `HUB_*` 变量，而且每台电脑的必要变量不同；按「名字固定的钩子 + 取值指向 workbuddy」去掉，范围小，规则可测
- **验证**：`tests/agent-env.test.mjs` 9 项（新增 4 项）；全量测试 437 通过，2 项失败是本机没装 ffmpeg 的已知项
- **没验证**：没在会出问题的电脑上试。文档作者自己也说单个变量注入的复现不稳定，所以不能保证这一刀一定修好；需要在干净机器（新机 / Windows 沙盒）上，由 WorkBuddy 会话拉起工作台，再跑 `codebuddy -p "只回复：PONG"` 和 `/api/bridge/test` 各一次。没修好的话下一步是找 CodeBuddy 官方给 CLI 独立的登录存储

- **浏览器方式的说明跟上现状**：以前「工作台独立浏览器」写着（推荐），并说登录账号、对标核实都用它——采集和登录核对停用它之后这是误导。现在「我自己的 Edge（WorkBuddy 插件，推荐）」排第一并写明小红书采集只走它；「工作台独立浏览器」改成「不能用于小红书采集」

## v0.8.12（2026-10-27）新设备上架验收发现的问题

来源：员工电脑给的新设备上架清单和自检脚本。对照源码在本机复现后修的。

- **浏览器方式不是 WorkBuddy 插件时，点「开始采集」当场拒绝并说明去哪改**（新机器的浏览器方式默认是 none，清单里最容易漏的一步）。以前点了返回成功，队列随后悄悄暂停，原因还写着「请在连接设置开启后台组件」——后台组件已经停用，这句话是误导。现在：服务端 409 + 「到连接与设置 → 执行 Agent 与浏览器，选 WorkBuddy 浏览器插件（按钮灰就先在 WorkBuddy 里打开让它控制浏览器）」；竞品对标的采集卡片里直接显示这条提示、带「去连接与设置选」的按钮，开始按钮灰掉
- **图片任务页面关着也会取回**：以前只有「图片创作」页开着才会查进度，页面一关任务就一直显示「进行中」，员工以为没成功、重复提交（白烧额度）。现在服务端每 10 秒查一次进行中的远端任务（只查已有任务编号的，绝不提交新的；超过 30 分钟的不自动查）
- **带参考图出图被拒 HTTP 413**：根因在中枢的 nginx（默认只收 1MB 的请求体，实测 1.9MB 就被拒），已在中枢修；工作台这边把 413 翻译成「图片太大，中枢没收下（每张参考图 ≤10MB…）」，不再只显示 HTTP 413
- 测试新增 3 项、改 2 项（浏览器方式不对时的 409、后台取回、413 提示、卡片提示）；对真实中枢验证了 413 修复（>1MB 的请求不再被 nginx 拦）
- **没验证**：员工电脑上真实升级到 0.8.12 后的表现；后台取回在真实出图任务上的效果

## v0.8.11（2026-10-26）采集节奏与额度；发布包；打开即换新版本

来源：员工电脑 2026-10-26 的反馈和他们的本地改动包（品牌号收到平台「浏览行为与真人操作习惯不一致」的提示）。逐文件对照 0.8.10 后吸收，其中几处改写了。

**事故原因核实**：10-23 18:09 那一批检查点的 `source` 全是 `agent-visible`，说明五篇笔记 44 秒读完的是 **agent 通过浏览器插件读的**，不是 Playwright 采集器（那个默认关着，那台电脑也没装）。当时手册只写了「有界随机间隔」，没有数字，agent 按自己的理解跑了；而 0.8.8 起「开始采集待办」在插件方式下也走 agent，队列里没有任何上限——这个缺口是 0.8.8 补路径时带出来的。

- **采集状态与额度**（`server/pace.mjs`，网页「竞品对标」的采集卡片里）：总开关（**默认关**）、冷静期、时段（默认 09:00–22:30）、每天上限（笔记 10 / 主页 3）、两次采集至少隔 180 分钟、一次会话笔记 ≤5 篇 / 主页 ≤2 个，全部可调（有边界）。「开始采集」「补齐」「核实主页」和队列自动接续目标前都在**服务端**检查，不满足就 409 并说明原因，不只是界面上拦；队列不会在后台悄悄等到点再继续，要人再点一次开始
- **账本由工作台自己记**：派发采集时记一次会话，检查点合并时按检查点**文件的写入时间**记主页和笔记（链接去掉 `xsec_token` 等参数再存）。不靠 agent 自己上报——CodeBuddy 的工具里没有 Bash，也写不了追加式审计
- **读得太快自动停手**：两篇笔记的检查点相隔不到 20 秒，就认定 agent 在连发：取消正在跑的 agent 任务、暂停队列、**自动关掉总开关**，要人确认后才能重新开。补合并的旧检查点（重启后）只记账不触发
- **策略放在状态目录**（接了中枢时是 `HUB_APP_STATE_DIR`，和访问锁一样 agent 碰不到）；文件损坏按「禁止」。员工电脑上旧补丁写的 `browse-cooldown.json` 第一次读时迁移过来，升级后冷静期不丢（旧文件里的「开」才算开）
- **冷静期**只能由人在网页里设 / 解除（设冷静期同时关总开关；解除冷静期不替你打开总开关）；`scripts/pace-check.mjs` 是只读检查（退出码 0 / 2 / 3），不能改任何设置
- **手册写成数字**：`playbooks/benchmark.md`「读取量与节奏」、`browser.md`：一次会话上限、两篇至少隔 25 秒、遇验证码立刻停；每次采集任务的提示词里也带这些数。没有采用的：「停留 25–70 秒并滚动 2–3 次」「要有回看、有中途离开」「不要直输网址」——那是在模拟真人行为，不是控制读取量；控制风险靠量少、限时段、人工确认
- **后台 Playwright 采集和登录核对停用，采集只走 WorkBuddy 浏览器插件**：Playwright 直连带自动化特征（`navigator.webdriver`、调试通道启动参数），且用的是工作台专用的浏览器资料。浏览器组件的 `verify` / `prepare` 直接拒绝；`POST /api/browser/worker` 开启、`benchmark.verify`、`browser.prepare` 都返回 409；队列选路只剩 agent；设置页显示「已停用」；「登录账号」「先核对登录账号」改为在自己的浏览器里登录，再由 agent 读一页号比对。图片封面渲染（headless Edge 画本地 HTML）不受影响。只有开发 / 自动测试设 `XHS_ALLOW_WORKER_COLLECT=1` 才放开。没有吸收的：浏览器上下文下载头像（带 Referer 模拟页面自己的请求）、读页面内嵌数据 `RENDER_DATA` 补互动数、拟人停留和滚动（这些是给 Playwright 路径做的，路径已停用）
- **发布包**：「下载全部素材」改为「下载发布包」（`-发布包.zip`）：图片 `01-封面` / `02-配图1`…、文案分【标题】【正文】【话题】三段、`发布步骤.md`（由本人在官方 App 完成每一步，工作台不代替也不向小红书发请求）。排期页每行、检查通过后都有下载入口。去掉了员工版里「账号行为更接近真人」「间隔 2 小时以上」之类没有依据的说法
- **打开即换新版本**：`start` 发现正在运行的是旧版本且没有任务在跑，就停掉旧的换成新版本（以前只提示「关闭后再打开」）；有任务在跑只说明、不打断。用版本号判断，不用「源码比进程新」（那是本机改代码才会遇到的）
- 「核对登录账号」「登录账号」在 WorkBuddy 插件方式下：提示在自己的浏览器里登录，再由 agent 读一页比对；不再弹安装浏览器组件的对话框
- 升级后第一次：采集总开关是关的（新版默认），要在「采集状态」里打开
- 只给开发 / 自动测试用：`XHS_PACE_RELAX=1` 关掉「时段 / 采集间隔 / 读得太快」三项（总开关、冷静期、每日上限仍生效）。生产里不要设
- 测试新增 25 项：节奏判定与账本、读太快、旧版冷静期迁移、状态目录、命令行只读、真实 HTTP（闸门、冷静期、读太快自动关总开关）、界面（状态卡、按钮只发接口请求）、打开即换新版本（空闲换、有任务不换）、发布包
- **没验证**：WorkBuddy 插件方式下真实跑一轮采集（按要求没访问真实小红书）；读太快的阈值（20 秒）在真实 agent 上会不会误停——若 agent 习惯读完几篇再一起写检查点，间隔会很短，需要看第一轮真实数据再调

## v0.8.8（2026-10-25）员工电脑自检发现的缺陷修复（XHS-01～04、08、10、11）

来源：员工电脑上的 agent 在 0.8.6 上打的本地补丁和自检清单（2026-10-25）。升级到 0.8.8 后那台电脑上的第 3～6 节本地补丁都不用再打。

- **XHS-01 删除一个素材会把整个素材文件夹移进回收站**（数据级）：`deleteMaterial` 给 `safeJoin` 传了三个参数，第三个被静默丢掉，实际移走的是 `materials/files` 整个目录。现在只移走这个素材自己的文件；`safeJoin` 多传参数直接报错，不再静默。已经中招的电脑：素材文件在回收站（数据目录 `.trash/materials/`）里，可以找回
- **XHS-02 浏览器方式是 WorkBuddy 插件时「开始采集待办」永远失败**：批量采集只认后台只读组件（Playwright），漏了 WorkBuddy 插件这条 agent 路径（单个「核实主页」本来就支持）。现在三条路：后台组件 → agent 浏览器（WorkBuddy 插件，按手册只读读页面）→ 都不行才拒绝；agent 路径超时 10 分钟（后台组件仍是 3 分钟）；采集中显示本轮走的是哪条路
- **XHS-03 对标观察读不到小红书号时整批被拒**：手册允许没看到的小红书号留空，服务端却要求必填，拒绝原因还是含糊的「观察字段不能为空」。现在身份以主页链接为准（`/user/profile/<id>` 是账号唯一 id）：双方都有小红书号时必须一致；没读到或已核实记录里没有时，昵称（忽略空白和大小写）必须和已核实记录一致，否则拒绝并说清原因。身份字段仍取已核实记录，检查点不能改写身份。手册 `benchmark.md` 同步写明
- **XHS-04 公司中枢出图 / 出视频下载断流就失败**：下载遇到网络中断或 5xx 自动再试两次（隔 1.5 秒、3 秒）；链接过期等 4xx 不重试
- **XHS-08 「登录账号」第一次会直接安装浏览器组件**：现在先弹窗说明装什么（只装 playwright-core，不下载浏览器，用本机 Edge / Chrome）并征求同意，可以取消
- **XHS-10 旧的 `browser.json` 误导 agent 拒绝打开页面**：手册 `browser.md` 写明它只是上一次的检查记录，不能据此拒绝打开页面，超过 30 分钟当作「未知」，每次实时核对后整份覆盖
- **XHS-11 只读档下发送回复 / 发布没有说明**：浏览器是只读档时，「评论私信」「发布排期」页顶部说明 agent 只能读和写草稿，正式发送、发布要本人在小红书里完成
- 测试新增 9 项（含真实 HTTP 删除素材）

### 视频复刻：描述任务的真实测试

- 真实测试（Claude Code 接入本机 deepseek / qwen 模型）发现：参考视频描述会**自信地编造**——把白色陶瓷杯说成“透明玻璃杯”，还编出不存在的手和字幕。直接问同一张图，这些本地模型要么按提示词里的颜色顺序照抄答案，要么诚实地说“看不到”。结论：这个功能必须配能看图的模型才可信
- 新增「看图自检」作为描述任务的第一阶段：生成一张随机排布的四象限色块图，让 Agent 报出每个象限的颜色，必须 4/4 答对才继续；答错立即终止，不再花几分钟去写一份看起来很详细的假描述，并说明答对几个、哪个象限错了，以及出路（换能看图的 Agent/模型，或直接手写描述，参考视频仍会一起提交）。真实测试里本地模型 30 秒内就被识别出来；通过后缓存 12 小时，换 Agent 或重新测试连接后重新检测。自检答案直接取 Agent 的最终回复，省去一次写文件的往返
- 描述任务提速：12 张抽帧拼成 2 张图（Agent 只读 2 张而不是 12 张），超时从 240 秒放宽到 300 秒；真实测试里原来逐张读图 240 秒超时失败，拼图后 118 秒完成
- 页面：描述分析中显示已用时间（每秒走动），失败后显示“重试”和原因（超时时给出可操作的建议）
- 视频任务（排队/生成中）显示已等待时间，并按模式给出预计时长（文生/图生通常 1–3 分钟，参考视频复刻通常需要几分钟）
- 真实验证：用文生视频的 3 秒成片当参考视频、第一张生成图当产品图，手写描述做参考视频换主体（rv2v，3:4，73 帧）：约 4 分 40 秒完成，原片的固定机位和热气上升节奏被完整保留，主体换成了姜黄粉玻璃罐；不依赖 AI 描述也能完成
- 自动化测试新增 16 项（vision-challenge、两阶段流程、拼图、缓存、回复解析、界面）

### 生图进度自动更新

### APIMart 提交失败诊断

- 生图提交失败不再丢失原因：记录失败阶段（connect/http/respond）、HTTP 状态、请求编号（x-request-id/cf-ray）和脱敏后的网关返回（自动替换 API Key 为 `***`），诊断信息随任务落盘，重启后仍可查看
- 区分「明确拒绝」与「结果不确定」：网关 4xx（408 除外）视为已拒单、未创建远端任务，可直接修正参数重试；断网、5xx、响应缺任务编号等记为「不确定」，提示先到 APIMart 控制台核对任务编号，避免重复生成重复计费
