# 更新日志

## v0.7.3（2026-10-21）向企业中枢自动上报工作成果

- 新增环境变量 `HUB_WORK_OUTBOX`：中枢接入器启动工作台时指定一个本机文件，工作台把关键产出追加写进去（一行一条 JSON），由接入器转发到中枢的「工作看板」，老板和主管能看到谁做成了什么、进度如何
- 目前上报两类：**笔记**（草稿 → 待发布 → 已发布，对应 进行中 30% / 待审核 90% / 已完成）和**对标拆解**（拆解完成）。只在状态变化时上报，修改正文不重复报；同一条用固定 key，重复上报是更新
- 只写标题、类型、状态、进度、公开链接和一句话说明，**不写正文、提示词、账号资料和本机路径**；没有该变量时什么都不做，任何写入错误都不影响工作台
- 自动化测试新增 5 项（hub-work）

## v0.7.2（2026-10-21）读取企业中枢的能力预检结果

- 新增环境变量 `HUB_CAPABILITIES_FILE`：中枢接入器打开本应用前会检查 CodeBuddy CLI、中枢模型、系统浏览器等依赖，把结果写进该文件。工作台每次用到都重新读取（装好依赖后不用重启）
- 缺浏览器能力时**只拦浏览器功能**（对标采集、浏览器准备、核验任务），直接说明缺什么、怎么处理；写笔记、看数据等照常。不记成平台风控，不上访问锁
- 「连接与设置」页新增「中枢能力检查」一行；竞品对标的采集卡片在缺能力时显示原因并禁用相关按钮
- 没有该变量、文件不存在或不合法时一切照旧
- 自动化测试新增 8 项（hub-capabilities，含桥层拦截）

## v0.7.1（2026-10-21）CodeBuddy CLI 适配与两档浏览器权限

在真实的 CodeBuddy CLI 2.171.0 + 企业中枢环境里测通了：连接自检、浏览器控制、对标采集与拆解、选题生成、笔记草稿。

- **CodeBuddy 适配**：提示词改走标准输入（Windows 上 `codebuddy` 是 .cmd 垫片，命令行参数里的多行文本会在第一个换行处被截断，agent 只看到标题）；无人值守用 `--permission-mode acceptEdits`，并显式放行 Read/Glob/Grep/WebSearch/WebFetch。`--allowedTools` / `--disallowedTools` 是多值参数，**每个工具名单独一项**（实测逗号拼成一项时放行不生效）。`browser-setup` 白名单加入 codebuddy
- **两档浏览器权限**（`adapter.browserMode`）：
  - **只读档（默认）**：点击 / 输入 / 填表 / 上传文件 / 按键 / 拖放 / 选择 / 执行脚本 / 弹窗处理等 14 个写类 Playwright 工具全部禁用（被禁的工具对 agent 不可见），只留打开网址、快照、截图、等待、查找、标签页等读取类工具——用于分析数据、学习博主帖子，不允许自动发布
  - **测试档**：放开点击、输入等交互工具；仍禁用上传文件和执行脚本，并用 Playwright MCP 的 `--blocked-origins` 屏蔽创作者中心（发布入口所在），所以发布做不了；点赞 / 评论 / 关注靠提示词约束，测完应切回只读档
  - 新命令 `node scripts/workbench.mjs browser-mode readonly|test` 一键切换；`applyBrowser` 对 CodeBuddy 幂等，关闭浏览器控制时一并去掉模式和屏蔽域名
- 自动化测试新增 6 项（codebuddy-browser，使用临时数据目录）

## v0.7.0（2026-10-21）跨平台可用、可升级、可接入企业中枢

这一版以“能发给别人用”为目标，经过 Windows 上的真实测试（真实 agent、WorkBuddy 值守、APIMart 生图、视频生成）打磨：

- **接入与安装**：agent 连接由用户选择（含 WorkBuddy 等桌面类），首次打开在网页里直接选；`doctor` 环境自检、安装流程重写；ffmpeg 等外部程序按系统常见位置查找
- **升级**：数据版本记录、升级前自动备份与迁移、`upgrade --package` 一条命令换新版（旧版保留可回退）
- **稳定性**：收件箱值守重启不丢任务、中文不乱码、断线自恢复；生图/视频自动更新进度与清晰的失败提示；修复 Windows 上视频保存失败
- **视频复刻**：描述任务提速（拼图）并加“看图自检”，不再展示模型编造的描述
- **企业中枢**：由中枢启动时（环境变量 `HUB_MCP_SERVERS_FILE`）自动让工作台里的 agent 接入公司知识库、岗位技能和 GPU 工具
- 体验：页面信息精简、统一的站内确认框、备份列表等细节

以下是各部分的详细记录。

### 企业中枢接入

- 由中枢的本机接入器启动工作台时设置环境变量 `HUB_MCP_SERVERS_FILE`（指向 `{"mcpServers": {...}}` 文件），工作台把其中的服务（如 `enterprise-hub`）并入底层 agent 的 MCP 配置：对话任务里的 Claude Code 可以使用公司知识库、岗位技能和出图出视频，权限、额度、审计仍由中枢强制执行
- 安全：只保留已知字段并校验类型，最多 8 个服务，文件超过 64KB 或不合法时忽略并在「连接与设置」显示原因；中枢不能覆盖工作台自己的 `playwright`；本地描述助手（`--strict-mcp-config`）和浏览器专用任务不加中枢工具
- 没有环境变量时一切照旧；「连接与设置」显示“企业中枢：已接入（enterprise-hub）”
- 自动化测试新增 10 项（hub-mcp）

### 收件箱模式真实测试（WorkBuddy 值守）

- 真实验证：WorkBuddy 读 SKILL.md 后进入值守，约 1 分钟内领取网页发出的任务并回写、结束（值守流程可用）。测出两个问题并修复：
  - **中文乱码**：WorkBuddy 回报“中文在传输中出现了乱码，落盘文本丢失 48 个字符”。Windows 终端按 GBK/UTF-16 解读 `inbox-next` 的标准输出。现在任务正文另存为 UTF-8（带 BOM）文件，输出里增加 `TASK_FILE: <路径>`，agent 以文件为准；回写正文自动识别 UTF-8 / UTF-16 / GBK；SKILL.md 补充了 Windows 下的读写方法
  - **处理中显示“离线”**：agent 领到任务后几分钟内不再轮询，界面会误报“等待 agent 值守”。现在领取后 15 分钟内有动静（领取或回写进度）都算在线
- WorkBuddy 值守后给出的问题清单（核对后全部修复）：
  - 入站编码：请求体按 UTF-8 → GBK 兜底解码，不再把非 UTF-8 调用方（例如 Windows 命令行里的 curl）发来的中文永久替换成 U+FFFD；已含替换字符的聊天消息直接拒绝并提示重发，不再交给 agent 去猜
  - 收件箱任务持久化：网页对话任务落盘（`run/inbox-tasks.json`），服务重启后恢复为待领取（重启前已被领走但没回写的也放回队列），对应的聊天气泡保持“等待”而不是被标成中断；超过 24 小时或文件损坏的不恢复
  - 长轮询等待者随连接断开清理：客户端断线后不会再把下一条任务“领”给已经不存在的客户端；新增 `inbox-requeue <taskId>` 退回队列
  - CLI 不再崩堆栈：连接被重置或服务重启时带退避重试（1s/2s/4s）并每次重新读取 server.json；仍不通时输出机器可读的 `WORKBENCH_DOWN`（退出码 2），与 `NO_TASK` 区分
  - `--help` / `-h` 只打印用法，不再真的领任务；新增 `inbox-next --dry-run` 只看队列
  - 在线判定：正在长轮询等任务时始终在线（一次长轮询最长 110 秒，原来每次中途都会闪成“离线”），领取后 15 分钟内有动静也算在线
  - 日志：启动记录父进程 pid、上一个实例是否还在、从磁盘恢复了几个任务；退出记录退出码；`stop` 命令记录是谁停的（Windows 上结束进程服务来不及自己写日志）；未捕获异常写入日志
  - `open` 在 Windows 上改用 `explorer.exe`，不再用 `shell: true` 传参（消除 DEP0190 告警）
- 自动化测试新增 3+8 项（inbox-encoding、inbox-recovery、服务端编码与接口）

### 视频复刻：描述任务的真实测试

- 真实测试（Claude Code 接入本机 deepseek / qwen 模型）发现：参考视频描述会**自信地编造**——把白色陶瓷杯说成“透明玻璃杯”，还编出不存在的手和字幕。直接问同一张图，这些本地模型要么按提示词里的颜色顺序照抄答案，要么诚实地说“看不到”。结论：这个功能必须配能看图的模型才可信
- 新增「看图自检」作为描述任务的第一阶段：生成一张随机排布的四象限色块图，让 Agent 报出每个象限的颜色，必须 4/4 答对才继续；答错立即终止，不再花几分钟去写一份看起来很详细的假描述，并说明答对几个、哪个象限错了，以及出路（换能看图的 Agent/模型，或直接手写描述，参考视频仍会一起提交）。真实测试里本地模型 30 秒内就被识别出来；通过后缓存 12 小时，换 Agent 或重新测试连接后重新检测。自检答案直接取 Agent 的最终回复，省去一次写文件的往返
- 描述任务提速：12 张抽帧拼成 2 张图（Agent 只读 2 张而不是 12 张），超时从 240 秒放宽到 300 秒；真实测试里原来逐张读图 240 秒超时失败，拼图后 118 秒完成
- 页面：描述分析中显示已用时间（每秒走动），失败后显示“重试”和原因（超时时给出可操作的建议）
- 视频任务（排队/生成中）显示已等待时间，并按模式给出预计时长（文生/图生通常 1–3 分钟，参考视频复刻通常需要几分钟）
- 真实验证：用文生视频的 3 秒成片当参考视频、第一张生成图当产品图，手写描述做参考视频换主体（rv2v，3:4，73 帧）：约 4 分 40 秒完成，原片的固定机位和热气上升节奏被完整保留，主体换成了姜黄粉玻璃罐；不依赖 AI 描述也能完成
- 自动化测试新增 16 项（vision-challenge、两阶段流程、拼图、缓存、回复解析、界面）

### 视频真实测试发现的问题

- 修复 Windows 上视频无法保存：生成的视频下载后，校验步骤只在 macOS 的 Homebrew 目录里找 ffprobe，Windows 上找不到就报“视频校验失败，请确认本机安装ffprobe”，任务卡在“连接或下载异常”。现在与参考视频抽帧共用同一套查找（PATH + 各系统常见安装目录）
- 修复 `binaries.mjs` / `doctor.mjs` 里 Windows 路径的反斜杠被当成转义（`C:fmpegin` 变成换页符+退格符、安装提示里 `%USERPROFILE%fmpeg` 显示异常）；新增测试防止回归
- 视频服务连接测试成功后，显示中文模式名（文生视频、图片动起来……）而不是 `["i2v","r2v",…]` 原始数组
- 真实验证：文生视频 3 秒 3:4（576×768、73 帧、24fps、H264+AAC），从提交到保存约 2 分钟，画面稳定

### 生图等待与失败提示

- 生成中显示「已等待 m:ss · 通常需要 1–2 分钟」，计时每秒走动但不重绘页面（“1–2 分钟”来自两次真实生成的实测，仅作参考）
- 参考图 / 画面要求会发送给第三方时，在「创建生图任务」按钮正上方给出醒目提示：APIMart 点明“发送给第三方 APIMart、不在本机完成”，当前 Agent 点明“交给它的生图工具”（图片创作页和封面编辑器都有）
- 失败路径（用故意填错的密钥对真实 APIMart 实测）修复三处：被拒绝时不再把上游 JSON 原样倒出，改为“原因 + 怎么处理 + 上游摘要 + 请求编号”（401 密钥无效、402 余额不足、403 无模型权限、429 限流、400 内容审核等都有对应指引）；被明确拒绝的卡片不再显示“查询进度”和矛盾的“请核对服务记录”，改成“这次没有创建任务，修改后可以重新提交”，密钥问题直接给“去检查 API Key”按钮；连接测试遇到偶发网络错误自动重试一次，仍失败时给出网络错误码和排查方向（原来只说“无法连接”）
- 自动化测试新增 6 项

### 生图进度自动更新

- 真实 APIMart 生图测试发现：提交后页面一直停在“正在提交 / 尚无任务编号，请核对服务记录；不要重复提交”，即使服务端早已拿到任务编号，也不会自动更新，用户必须手动点“查询进度”甚至刷新页面。现在图片创作页和封面编辑器里的生图任务会自动更新：刚提交还没编号时只重新读取记录，有编号后只调用只读的查询接口（绝不重新提交、不会重复计费），完成后自动出图
- 轮询节奏：前 2 分钟每 4 秒，之后每 10 秒，出错退避到 30 秒，超过 30 分钟的任务不再自动查询（仍可手动查询）；用户正在文本框里输入时只更新数据不重绘（最多推迟 20 秒；下拉框有焦点不算输入，第二次真实测试里下拉框的焦点曾让页面一直不刷新，已修）
- 提交中的提示改为“正在提交，稍等几秒；不要重复点击”，有编号后写明“只查询原任务，不会重新提交，也不会重复计费”
- 自动化测试新增 9 项（image-polling）

### 首次连接体验

- 点击任何「让 agent …」类操作而尚未连接时，弹出选择窗口并记住这次操作，连接完成后点「继续刚才的操作」才发送（桌面类 agent 会先给出要对它说的那句值守口令和复制按钮）
- 新手引导第 1 步去掉命令行黑话，改成「选择 agent」按钮；默认账号名「我的账号」时概览问候改为「你好」
- 自动化测试新增 8 项（connect-ui）

### 升级机制

- 数据目录新增版本记录（`config/version.json`：程序版本、数据格式版本、升级历史）；版本变化时启动前自动备份（`upgrade-*.zip`），再按序执行迁移；迁移失败不推进版本、保留备份并在网页显示原因，下次启动重试；备份失败则不迁移
- 数据来自更新版本时（程序被换成了旧包）拒绝启动，不改动任何数据
- 新增 `upgrade --check` 与 `upgrade --package <zip> [--yes]`：预检安装包（完整性、版本、路径安全），备份后替换技能包，旧版本保留为 `.bak-<版本>`，失败自动回滚
- `setup` 在全新数据目录里立刻登记版本，避免服务误判为旧版遗留数据
- 版本号集中到 `server/version.mjs`；「连接与设置」显示版本、数据格式与最近升级记录
- 自动化测试新增 17 项（upgrade）

### 环境自检与安装流程

- 新增 `doctor [--json]`：检查 Node、数据目录、ffmpeg/ffprobe、Agent 连接，缺项直接给出按本机包管理器（winget / choco / scoop / brew）选好的安装命令，最后一行 `RESULT: ok | action-needed | blocked`，agent 照输出执行即可
- ffmpeg / ffprobe 改为先查 PATH、再查各系统常见安装目录（含 Windows 的 WinGet、用户目录解压位），刚装完未重开终端也能找到
- SKILL.md 安装流程改为：检查 Node → `doctor` → 初始化 → 启动；明确“装可选依赖前先告知影响与体积、需要密码/管理员权限的步骤由用户本人操作、装完必须用 doctor 复核”

### Agent 连接选择

- 本机同时有多个可用 agent（如 Claude Code 命令行 + WorkBuddy 桌面应用）时，`bridge-test` 不再默认挑第一个命令行，而是输出 `RESULT: choose` 让用户决定；已有选择重跑时沿用，不会被别的 agent 悄悄改掉
- 新增桌面类 agent（WorkBuddy、Cursor、Trae）探测，连接走收件箱模式并记录由谁值守；`--agent <id>` 明确指定，`--auto` 保留旧的自动挑选
- 网页「连接与设置」自动列出本机检测到的 agent 及各自模式（CLI 无需保持窗口 / 收件箱需窗口常开），一键切换；离线提示点名具体 agent

- 自动化测试新增 6 项（agent-selection）

### APIMart 提交失败诊断

- 生图提交失败不再丢失原因：记录失败阶段（connect/http/respond）、HTTP 状态、请求编号（x-request-id/cf-ray）和脱敏后的网关返回（自动替换 API Key 为 `***`），诊断信息随任务落盘，重启后仍可查看
- 区分「明确拒绝」与「结果不确定」：网关 4xx（408 除外）视为已拒单、未创建远端任务，可直接修正参数重试；断网、5xx、响应缺任务编号等记为「不确定」，提示先到 APIMart 控制台核对任务编号，避免重复生成重复计费
- 已有诊断的任务再次刷新时保留原始失败原因，只补充本轮结论，不再被固定文案覆盖
- 自动化测试新增 4 项回归（拒单、断连、缺编号、查询 404）
